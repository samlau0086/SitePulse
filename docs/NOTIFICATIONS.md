# Email, Bark, Slack and Telegram notifications

## Slack and Telegram

Multiple labeled Slack Incoming Webhooks and Telegram bot/chat pairs are supported. All four channels share the 20-active-endpoint limit, 60-second destination cooldown and 10-per-hour workspace verification/test budget. The same owner/admin and server membership checks apply. Each destination requires explicit single-use, one-hour opt-in before routine alerts; resend replaces the proof. Group/channel confirmation proves message access, not account ownership or workspace membership.

Slack accepts only `https://hooks.slack.com/services/...` with three validated path segments and no query, fragment, credentials, alternate port or proxy. Telegram accepts a validated bot token and numeric chat ID and posts only to `api.telegram.org`. Requests disable redirects, have a ten-second timeout and bound success bodies to 32 KiB. Slack messages use plain-text blocks; Telegram does not enable parse mode. Provider bodies and network exceptions are never persisted. These channels cannot target arbitrary tenant-provided hosts.

Configure the same optional stable 64-character hex `NOTIFICATION_ENCRYPTION_KEY` on API and worker, independently of `BARK_ENCRYPTION_KEY`; generate it with `node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"`. Missing configuration disables chat creation/sending only. Secrets are AES-256-GCM encrypted with organization- and channel-bound authenticated data. Channel-prefixed SHA-256 fingerprints provide uniqueness and queue addressing but are hidden from reads. Reads show labels and a hidden-credentials notice; deletion clears ciphertext. Back up the key separately and do not rotate without re-encryption or re-adding destinations. Migration `0010_flawless_morg` expands existing constraints without changing earlier migrations.

Each sweep claims up to five rows **per channel** (20 total across four channels). Chat uses the existing durable outbox, lease fencing, recipient revalidation and at most eight exponentially delayed attempts. Local `slack:<deliveryId>` / `telegram:<deliveryId>` markers record handoff, not provider receipts. No provider idempotency guarantee is made: ambiguous timeouts or crashes after acceptance may duplicate a message. HTTP 429 currently uses the same bounded backoff; Retry-After is not consumed. Monitoring failure confirmation timing is unchanged.

Acceptance: configure two destinations per channel, confirm each opt-in, reject replay and superseded proofs, then test after cooldown. Trigger a controlled incident and recovery; check one message per destination under normal operation. Disable/delete a recipient with a queued event and verify suppression; confirm another workspace cannot read or mutate it. Automated provider tests mock HTTP and never use real credentials; real Slack/Telegram delivery must be accepted after deployment. See README for bot permissions and Chat ID discovery.

Confirmed incidents and confirmed recovery events enter a PostgreSQL outbox in the same transaction as their incident state change. A single open incident emits one opening event per verified destination; HTTP/SSL recovery is emitted only after two consecutive successes. Connector `stale_data` warnings open after the server heartbeat-stale threshold and recover after one authenticated, non-replayed heartbeat, with independent Connector offline/restored wording. Connector freshness never asserts HTTP availability. A connection reset is not described as recovery and does not send a recovery message. See [responsiveness configuration and acceptance](MONITORING_RESPONSIVENESS.md).

The `/app/notifications` sidebar destination manages recipients per workspace. Verified owners/admins may change settings, add email recipients or multiple labeled Bark/Slack/Telegram destinations, resend verification, enable/disable/delete recipients and send tests; other members are read-only. Platform allowlisting does not grant tenant access. The member directory comes from authenticated membership checks. The 20-active-endpoint limit and the persisted 10-per-hour verification/test budget are shared across all four channels.

The Bark integration accepts a device key only and always posts to the official `https://api.day.app/push` endpoint. Full URLs, custom hosts and self-hosted Bark servers are rejected in this milestone, so the feature does not create a tenant-controlled outbound URL or bypass the monitoring SSRF policy. The API stores a SHA-256 fingerprint for uniqueness and encrypts the raw key with AES-256-GCM using `BARK_ENCRYPTION_KEY` and organization-bound authenticated data. Reads return only the label and a hidden-key placeholder; deletion clears ciphertext. Audit logs, queue rows and provider errors never contain the raw key.

Verified-member delivery defaults on and can be turned off independently. Managed destinations override automatic member delivery for the same normalized address, even when pending, disabled or soft-deleted (a tombstone prevents fallback). Active enabled verified destinations are unioned with remaining automatic members and deduplicated before enqueue. A new recipient receives future events only. Removing an endpoint never removes a user or workspace membership. Re-add and reverify a deleted destination to resume delivery.

The worker revalidates the recipient before each provider call, including retries. Disabled/deleted endpoints, disabled member delivery and revoked/unverified memberships suppress pending messages with `RECIPIENT_DISABLED`. In-flight/provider-accepted mail cannot be recalled. A managed endpoint authorizes delivery independently of membership, so removing a member does not disable their separately verified managed endpoint. An automatic delivery superseded by any managed row is suppressed rather than rerouted.

Verification is a separate destination opt-in, not an authentication/session protocol: random 256-bit token, hash-only storage, one-hour expiry, endpoint scope, single use, replacement on resend and invalidation on deletion. The public confirmation page removes fragment credentials from browser history and requires an explicit click; it grants no tenant access and does not enable disabled endpoints. GET never verifies. Trusted Origin is required for all mutations, including confirmation.

Up to 20 active endpoints are allowed per workspace. Verification and test requests share a persisted 60-second endpoint cooldown and 10-per-hour workspace budget, serialized under the organization lock across API replicas. Rejected/failed provider attempts consume the budget; duplicate/invalid requests roll back without sending. Verification/test messages are handed synchronously to the selected provider with a bounded timeout and no automatic retries; saved recipients survive provider failure. Owners/admins may retry after cooldown. Test messages are clearly labeled and require enabled verified endpoints. Provider acceptance is not inbox, APNs or on-device display confirmation.

Migration `0007_neat_morlun` introduces settings/endpoints and delivery organization/endpoint references, backfilling historical organization IDs through incidents/sites. Migration `0009_melted_jigsaw` adds endpoint/delivery channels, labels and encrypted Bark keys while defaulting existing rows to email. Unresolvable orphan deliveries are suppressed, not blindly sent. Audit records include actors and endpoint IDs/settings changes, not destination addresses, proof tokens, device keys or provider responses. Endpoint rows are soft-deleted for delivery fencing; Bark ciphertext is cleared on deletion while tombstones remain until workspace deletion. No customer production migration is run by this milestone.

The worker claims separate bounded batches of up to five rows per channel with `FOR UPDATE SKIP LOCKED`, records a 60-second lease and a random lease token, and releases database locks before calling providers. Completion updates must match the lease token so an expired worker cannot overwrite a newer attempt. The event key is unique in the database and is also sent to Resend as its idempotency key. Bark, Slack and Telegram have no verified provider idempotency key in this integration: an ambiguous timeout or worker crash after provider acceptance can produce a duplicate on retry. Transient failures retry with exponential backoff from 30 seconds to one hour, for at most eight attempts; exhausted deliveries become `failed`. Provider response bodies are discarded for non-success responses. Only a provider message ID or a local handoff marker and a fixed error code are persisted. Provider handoff is not proof of recipient delivery.

Local development uses the existing `AUTH_MAIL_TRANSPORT=file` setting and writes email alerts to `.local/alert-mail` with restrictive permissions. Production email requires `AUTH_MAIL_TRANSPORT=resend`, a verified `AUTH_MAIL_FROM`, and `RESEND_API_KEY`. Bark is optional in every environment and requires one stable 64-character hex `BARK_ENCRYPTION_KEY`; Compose gives the same validated key to API and worker. Back it up separately from the database and never commit it. Losing or rotating it without re-encrypting data makes existing Bark devices unusable; restore the old key or delete and re-add those devices. The worker sends queued notifications even if `MONITORING_ENABLED=false`, allowing delivery retries while probes are paused.

## Staging acceptance

Follow the executable [staging email acceptance runbook](NOTIFICATION_ACCEPTANCE.md) for GitHub configuration, controlled failure/recovery, read-only delivery queries, retry isolation and an evidence template. Record provider handoff separately from actual mailbox receipt.

1. Confirm a verified account belongs to the test organization's membership and an unverified account is excluded.
2. Trigger a controlled HTTP/SSL failure that crosses the confirmation threshold. Verify one opening message per verified member and one delivery row per unique event key.
3. Keep the incident failing across additional checks; verify no duplicate opening message is sent.
4. Restore the endpoint and cross the recovery threshold. Verify one recovery message per verified member.
5. Cause a provider rejection in a non-production test environment. Verify sanitized error state, a future retry time, and eventual sent/failed terminal state without exposing provider response content.
6. Add two Bark devices, complete each explicit opt-in, and verify each opening/recovery event reaches each device once under normal operation. Disable one and verify its queued event is suppressed.
7. Verify another organization's email or Bark device is never a recipient. Do not use customer production sites for fault injection.

Run `pnpm check`, `pnpm test:integration`, `pnpm build`, and `pnpm compose:check` before deployment. Staging database migration requires a successful pre-migration backup; production deployment requires separate authorization.
