# SitePulse UI implementation guidelines

Read [DESIGN.md](../DESIGN.md) before creating or modifying UI. It is the visual source of truth; apply its visual vocabulary to SitePulse rather than copying OpenCode branding, commands or functionality.

## Shared primitives

The October 27, 2026 SitePulse product direction in DESIGN.md overrides the original reference rules in this section for authenticated screens. Use system sans-serif `--font-ui` in the product and authentication forms, inline SVG `Icon` primitives, blue primary actions, white panels on `--product-background`, `--radius-panel` (14px) and `--radius-product-control` (8px). Public marketing retains the original cream/monospace reference. Product status badges use icons plus words instead of ASCII prefixes. Use card-based overview sites, the `ConnectionSummary` count-based donut with textual legend, and the attention panel; retain full-directory search, filtering and destinations. Do not invent historical graphs or treat connector activity as HTTP health. Product metric and action colors must use shared product/semantic tokens and pass the contrast tests. The original reference rules below apply wherever this product override does not specify otherwise.

- Reuse CSS variables in `apps/web/app/globals.css` for colors, fonts, control radius and section spacing. Extend existing primitives before adding a new variant. Avoid route-specific palettes.
- Use the shared monospace stack for every text role, including native form controls. Berkeley Mono is commercial and is not distributed with this repository. It is used only when available locally; IBM Plex Mono and system monospace fonts are fallbacks. Do not silently download or bundle an unlicensed font.
- Use the warm canvas (`#fdfcfc`), ink (`#201d1d`), soft neutral surfaces and 1px hairline borders. Containers stay square; interactive elements use 4px corners. No shadows or gradients.
- Use 38px/700/1.5 for public hero headings, 16px body and section headings, and 14px metadata. Reduce hero headings to 28px on mobile. Keep tracking at zero.
- Public sections use 96px spacing, reduced to 64px on tablets and 48px on mobile. Operational screens retain denser layouts for tables and controls, with 16px container padding and 48–64px section separation.
- Use ASCII markers such as `[+]`, `[!]`, `[x]` and `[-]`, not decorative icon sets. Keep visible status words and accessible names; decorative markers should be hidden from assistive technology where rendered as markup.
- Keep primary actions monochrome and secondary actions outlined. Semantic colors are reserved for operational/error signals, accompanied by text or markers. Never use color alone to communicate state.
- Dark content surfaces are reserved for one illustrative terminal preview on a public page. Product cards and navigation remain light.

## Existing layouts

Reuse `.page-heading`, `.metric-grid`, `.directory`, `.directory-toolbar`, `.status-badge`, `.site-tabs`, `.creation-form`, `.card`, `.secondary` and `.auth`. Keep mobile directories readable with labeled stacked rows, keyboard focus visible, and inputs at 16px to avoid mobile browser zoom. Controls should be at least 40px high, with comfortable link padding. Avoid horizontal page overflow; wide data tables and tabs may scroll inside their own container.

Homepage illustrations must be labeled as examples and must not invent live customer data or operational health. Authentication, server membership checks, API contracts, mutations and destructive confirmations must retain their existing behavior during visual changes.

Reuse `PlanUsage` for workspace plan and site allowance displays. Show the effective allowance, used slots and a textual full/over-limit message. Disable site creation when the fetched allowance is full while retaining server quota checks and errors for concurrent changes. Existing sites remain accessible after a downgrade.

Notification settings use the direct `/app/notifications` sidebar destination and a workspace selector rather than nested workspace navigation. Show member-default status, recipient channel, label, verification/enabled state and all available commands in the same view. Keep member reads visible but disable management controls when `canManage` is false. Email addresses must wrap; Bark rows show a label and hidden-key notice, never the device key or its fingerprint. Action groups must wrap at narrow widths, destructive removal requires confirmation, and verification links must use the public confirmation page without implying account or workspace access.

## Visibility and feedback

Attachments reuse shared cards and wrapping action groups for personal Google Drive. New uploads use Drive exclusively: omit the storage selector, explain metadata-only persistence and disable upload until connected. Display saved connection state, explicit reconnect/disconnect controls, original-file retention guidance and per-package storage, labeling old database entries as legacy. Confirm disconnect impact and library deletion; disable read-only mutations. OAuth errors must contain no provider codes, state or credentials. Keep connection status distinct from live file availability.

Directory health areas link directly to monitoring/security details. The summary strip counts only sites matching the current name/workspace filters and treats HTTP, security review (reported risks or local indicators), and Connector activity independently; missing evidence never implies health. Separate site name, hostname and workspace for scanning. Compact `Timestamp` displays may separate date and clock while retaining year, seconds, instant-specific GMT offset, full localized accessible text and localized/UTC tooltips; show the saved region time zone once above the group. Software cards show reported plugin/theme/update counts with unknown placeholders before first inventory. Keep last-success time, sync controls and failure causes visible; place secondary poll/request/attempt times in a native keyboard-accessible disclosure. Counts describe saved inventory, not a fresh collection or a security guarantee.

Email branding uses the shared form, fieldset, panel and feedback primitives on Preferences and platform administration. Show saved account ownership/plan eligibility, the lower-tier platform fallback, a bounded logo preview and explicit HTTPS image-host guidance. Public branding logos are a narrow exception to arbitrary image restrictions: no server image fetching or proxying. Templates use email-compatible tables/inline styles corresponding to the product palette, a visible brand name even without images, clear event wording, action buttons and a copyable fallback link. See [email branding](EMAIL_BRANDING.md) for authority and delivery rules.

Severity filter cards use the secondary button variant to avoid the global primary-button fill, with stacked severity/count content and a distinct selected border/background. Software site cards separate identity and management readiness, labeled timestamp metadata and a wrapping sync footer; badges keep their intrinsic width. Single-site views show identity without a disabled selection checkbox; cross-site views retain labeled selection checkboxes. Keep Connector setup/timing guidance in an accessible disclosure below the site cards.

Personal preferences live at `/app/settings` with a direct Preferences sidebar link. Use the shared form/panel controls, labeled native zone selector, explicit browser-zone button, pending fieldset and announced save/error feedback. Saved account time zones apply across workspaces. Use the shared `Timestamp` and layout `TimeZoneProvider` for operational times: full date/seconds, named zone and instant-specific UTC offset, original ISO value in `dateTime` and UTC tooltip. Normalize zero-offset labels to `GMT` across runtime/ICU versions. Keep SSR and hydration deterministic with an explicit zone/locale; never use the browser or server default implicitly. Missing times retain contextual empty states. Settings change display only; no schedule or notification changes.

Site directory rows and overview cards show independent Website, Security and Connector signals. Use HTTP job state, not heartbeat or historical incidents, for UP/DOWN; distinguish first failure, recovery confirmation, pending, disabled and schedule-overdue results. Show last-probe and assessment timestamps. Security summaries display highest environment/advisory severity, total risk count and separate unscored local indicators; retain pending/unavailable/stale/incomplete coverage caveats and never label an unknown result clean or safe. Keep mobile data labels and direct Monitoring/Security links.

Security assessments use bordered finding cards and shared semantic tokens: filled danger Critical, tinted danger High, warning Medium, informational Low and neutral Unknown badges with icons and words. Sort advisories by severity and show environment/advisory counts separately from unscored local indicators. Severity summary tiles are native buttons with visible selected state and filter only scored environment/advisory findings; keep unscored local indicators, coverage caveats and assessment freshness visible. Remove only exact duplicate records. If distinct advisory IDs share a provider title, component, severity and fixed boundary, group them visually but expose every ID and available source. Each finding gets a labeled Recommended action; distinguish hosting-level PHP work from software management, absent patches and supply-chain review. Never imply automatic remediation, classify a local indicator as confirmed malware or present one advisory boundary as fixing every issue. Keep cards and metadata responsive, paths wrapping and action links at least 44px high.

Inventory feedback is independent of heartbeat and management readiness. Use a visible per-site Sync inventory action outside selection labels; distinguish it from Reload results. Explain next-poll/Cron delivery, never-synced versus genuinely empty inventory, pending/timeout/failure and retained last-success timestamps. Only accepted inventory uploads establish success; read-only members cannot queue collection.

Slack and Telegram share the direct notification settings page and recipient actions. Use password inputs for webhook URLs and bot tokens, clear credential fields on submit, and show only labels and hidden-credential notices afterward. Telegram Chat IDs remain text inputs to preserve signed IDs exactly. Reuse existing form, fieldset, pending, read-only, error and confirmation patterns; channel verification grants no workspace access.

Monitoring distinguishes first failure awaiting confirmation from confirmed down. Connector `stale_data` events use Connector offline/restored wording and the shared connection icon; never render them as SSL errors or HTTP DOWN/UP. Explain independent website availability and valid-heartbeat recovery, including historical outcomes.

The single-site incident history uses a labeled fieldset of All statuses / Active / Resolved filter buttons instead of a native dropdown. Reuse the shared segmented button styles with `aria-pressed`, visible keyboard focus and 44px targets. Allow wrapping on narrow screens and reset the incident page when changing filters.

- Reuse `IncidentSignal` for incident outcomes: HTTP incidents show a directional icon plus DOWN until confirmed recovery, then UP. Retain lifecycle status separately. SSL uses certificate wording; reset/unknown closures must say recovery unverified. Explain that historical event states do not report current availability. Use semantic icon tiles and visible words together.

- Use the shared `PageSkeleton` in route `loading.tsx` boundaries, choosing overview, directory, workspaces, detail or form geometry. Keep the app shell visible and placeholders non-interactive and `aria-hidden`, with one screen-reader loading status and `aria-busy` on the content. Reuse `--skeleton-fill` and product panel tokens; disable the pulse under `prefers-reduced-motion`.

- Keep primary product buttons blue-filled with bold labels and secondary actions visibly outlined. Public primary controls remain ink-filled. Controls have a 44px minimum height; use `--border-control` rather than decorative `--hairline` for input and action boundaries. Disabled buttons retain readable labels and dashed borders, including inside disabled fieldsets, without enabled hover/pressed styling.
- Keep product action links underlined; directory row actions also have outlined touch targets. Active sidebar items use bold blue text/icons on a light blue fill and retain `aria-current="page"`. Do not add a trailing dot for selection; dots are reserved for actual unread or pending notifications. Site tabs use icon-based rounded segments with an informational blue fill and outline for the active destination. Monitoring uses independent HTTP/SSL cards and five-record check/incident pagination rather than long lists; preserve full timestamps, incident semantics and explicit loaded-record limits. Single-site software views retain site navigation and show only that site's inventory, with a separate cross-site management link. Keyboard focus uses the shared high-contrast outline.
- Use the shared `--success-*`, `--warning-*`, `--danger-*` and `--info-*` ink/surface pairs for operational signals. Status badges retain words and ASCII markers as well as color. Do not use the bright illustrative terminal colors for small text on light surfaces.
- Errors (`role="alert"`) and paragraph feedback (`role="status"`) get bordered, tinted panels with a stronger leading edge. Status feedback is informational, not automatically successful. Quota warnings use `.notice-warning`; verification banners use warning tokens. Keep inline result counts compact. Report failed connector actions as alerts, separately from informational pairing feedback. Destructive connector actions use `.secondary.danger` and retain confirmation dialogs.
- Verify text contrast of at least 4.5:1 and control/focus boundaries of at least 3:1 against adjacent light surfaces; keep these palette checks covered by unit tests.

## Verification workflow

Sync details summaries retain native disclosure markers and keyboard behavior. Keep their clock SVG inline-block and vertically aligned with the label so the global SVG reset cannot split the marker, icon and text onto separate lines.

Software controls follow per-site queued/running/unknown operations, not only HTTP submission state. Show a shared warning badge with visible queue state and action beside each affected installation; retain reported Active/Inactive inventory until refreshed. Exclude busy sites from direct/bulk/install targets and disable submission if none remain. Keep other sites usable, show exclusion guidance, and preserve acknowledged queued feedback if reload fails. Ignore polling reads started before a new queue acknowledgement. Rehydrate locks from server reads, retain them until terminal results or explicit unknown review, and include outstanding operations even beyond the recent-history window.

Plugin/theme management uses a direct `/app/software` destination plus a site-detail link, with workspace/site selection, responsive software cards and an adjacent command panel (stacked on mobile). Show real installed versions and per-site results, never optimistic execution success. WordPress.org plugin icons may load from fixed `ps.w.org` paths with no referrer and fall back to shared SVG artwork; this is an explicit product image exception. Do not accept arbitrary icon URLs. Require a reason, explicit preview and confirmation, invalidate previews on edits, show affected site names and backup/data-loss warnings, and keep management read-only for members. Unknown outcomes require explicit manual-review confirmation; cancelling affects unstarted tasks only. Reuse shared status colors, visible labels, focus, 44px controls and panel tokens.

The package library uses the direct `/app/attachments` destination and workspace selector. Keep upload type and ZIP input together; present the ZIP input as a keyboard-accessible drag-and-drop target that also opens the native file picker, shows the selected filename/size and waits for explicit **Upload and scan** submission. Detect the root slug on the server during scanning without a manual slug input; show the 8 MiB/package, 100-package and 64 MiB workspace limits before submission. Package cards show type, name/version, size, time, SHA-256, scanner version and human-readable blocking state. Never label a clean static scan “safe”; use “no selected patterns detected” and retain the warning that static inspection is incomplete. Findings remain visible but cannot offer an install action. Members may read metadata but upload/delete/install controls require `canManage`. Deletion needs confirmation and must explain that existing site installations are unaffected. Installing a reusable package links into the existing software manager with an explicit **Scanned upload** source, immutable name/version/fingerprint in the preview and the same site/reason/confirmation workflow. Do not render arbitrary uploaded artwork or source text.

Installed component action buttons must open a direct native modal confirmation without changing bulk selection or fields. Explicitly center native dialogs using fixed positioning, zero insets and auto margins so CSS resets cannot remove centering; retain at least 16px viewport margins and internal scrolling for long content. Use separate labeled Add to bulk arrow buttons and component checkboxes with 44px label targets. Provide Select visible (including indeterminate state), selected counts, explicit hidden-search selections and per-item removal; clear component selection on site/type changes. Confirmations list exact eligible component/site pairs, require a reason and server preview, invalidate on edits, and require a replacement theme for deactivation. Display sequential execution progress and a stop-remaining action, explaining that leaving the page stops unsubmitted components but not queued work. Never equate queue submission with success or allow UI shortcuts to bypass server authorization.

Platform administration has a direct conditional sidebar link `/app/admin`, bounded search and an inline editor. Reuse `PlanUsage` for before/after impact. Require a reason, invalidate previews on edits, disable pending operations, announce errors/success and require a fresh preview after conflicts. Focus the editor heading when opening it. Page guards and hidden navigation are convenience only; the API independently checks platform authority. Use shared tokens and fieldset primitives.

Review public and authenticated routes at desktop and mobile widths, including empty states, filters, errors and focused controls. Run `pnpm check`, `pnpm test:integration` against the dedicated disposable database, `pnpm build` and `pnpm compose:check`. Report any unavailable checks explicitly. Update README.md, CHANGELOG.md and these guidelines when shared UI behavior changes.
