# Personal Google Drive attachment storage

New plugin/theme ZIPs are stored exclusively in the uploading user's Google Drive. SitePulse processes bytes transiently for scanning and delivery and persists only metadata, scan results, SHA-256 and account/file references for new uploads. There is no database-byte fallback. Existing database attachments retain read/install compatibility and are not automatically migrated or deleted. Identical bytes reuse the existing workspace entry, including legacy packages; this does not create or migrate an attachment. All entries share the 8 MiB upload, 100-package and 64 MiB workspace limits.

## Setup and deployment

1. Enable Google Drive API in a Google Cloud project, configure its OAuth consent audience/test users, and create an OAuth web application. Register exactly `APP_ORIGIN/api/v1/auth/callback/google` using the actual origin, including local development port where applicable.
2. Configure both `GOOGLE_DRIVE_CLIENT_ID` and `GOOGLE_DRIVE_CLIENT_SECRET` to enable new uploads. Leaving both empty lets the app start with legacy reads but prevents creating attachments. GitHub deployment reads them as environment secrets and passes them only to the API. Restart after configuration changes.
3. Back up before applying pending migrations, including `0017_bored_sunspot.sql` for references and `0018_flawless_veda.sql` for the Drive default, through the deployment workflow. Existing bytes are preserved. Production migration/deployment requires explicit authorization.
4. Keep `GOOGLE_DRIVE_CLIENT_ID` and the corresponding Google OAuth project stable after uploads. Changing the OAuth app can make previously created `drive.file` packages inaccessible even when the user signs in with the same Google email.
5. Keep `BETTER_AUTH_SECRET` stable and backed up securely; Better Auth uses it to encrypt OAuth access/refresh tokens. Database backups contain encrypted credentials and references, not Drive ZIPs. Back up important Drive originals separately. Rolling back to an older API after Drive uploads requires a compatible API or explicit export/migration plan.
6. In Attachments, connect the Google account matching the verified SitePulse email and grant offline file access before uploading. There is no storage selector. The status shows saved credentials, not live provider availability. Reconnect the same account after authorization/refresh failure. Missing connection/configuration or provider failures never switch uploads to database storage.

## Authorization and lifecycle

Better Auth handles explicit account linking, state/PKCE and encrypted tokens. The app requests `drive.file` plus Google's identity scopes, offline access and consent. No Google signup or generic social-login/token HTTP endpoint is exposed. Linking grants no workspace membership. References bind the original SitePulse uploader and Google subject; connecting another Google account cannot read prior packages.

Uploads require current verified owner/admin membership before any Drive request and use the existing bounded ZIP scan first. Files are created in the user's Drive without a public sharing operation. Library reads return storage type, metadata and findings, never Drive IDs, credentials or bytes. Other workspace administrators can install through existing permissions while the original uploader remains a verified owner/admin; demotion or removal prevents installation.

Preview now reads the Drive package and verifies its size and SHA-256 before creating a confirmation preview. Confirmation, local opt-in, queue and short-lived site-bound lease remain unchanged. The API alone accesses fixed Google HTTPS endpoints, disables redirects and applies bounded streaming and 10-second request timeouts. Resumable upload session URLs must stay on the fixed Google upload endpoint. Downloaded size and SHA-256 must match the scanned upload. The Connector still downloads from its paired SitePulse origin and rechecks SHA-256. No Connector upgrade is needed for this storage option; uploaded packages already require Connector 0.4.0 and both local permissions.

Missing, modified or inaccessible files, revoked authorization or a missing original account block preview. Preview returns a sanitized explanation distinguishing configuration, account/scope/token, network, HTTP 401/403/404/429, response size/stream and changed bytes. Preview checks availability at that moment; a later file or authorization change can still fail installation, so delivery reads and verifies the file again. No persistent byte cache or public URL fallback is used. Existing WordPress installations are unaffected.

Disconnect clears the user's linked Google OAuth credentials from SitePulse while retaining the provider identity used by existing attachment bindings; it does not revoke the entire app grant at Google. Users can also revoke access in Google account settings. Disconnect and library deletion keep originals. Live operation references still prevent library deletion. Reconnecting the same account restores access if the original file remains unchanged and the same OAuth app is still configured. Existing account rows with a missing stored scope remain usable after reconnect because Better Auth may refresh tokens without rewriting the scope column.

Failed uploads and database rollbacks attempt to delete newly created files. Process crashes or failed cleanup can leave orphans requiring manual Drive review. Bounded provider calls hold the workspace quota lock, so slow responses can delay concurrent uploads in that workspace.

## API and acceptance

- `GET /api/v1/me/google-drive`: authenticated user's `{enabled, connected}`.
- `POST /api/v1/me/google-drive/connect` with `{}`: verified session and trusted Origin; authorization URL/state cookie.
- `DELETE /api/v1/me/google-drive`: verified fresh session and trusted Origin; disconnect own account only.
- `GET /api/v1/auth/callback/google`: narrow Better Auth callback; final redirect strips OAuth codes/state/provider errors. Reverse proxies must not log callback query strings.
- Attachment upload defaults to Google Drive when the query is omitted and still accepts `?storage=google_drive`. Explicit `?storage=database` is rejected with 400. New rows always have `zipBase64: null`. Metadata includes `storage` to distinguish legacy entries; Connector package delivery is unchanged.

Package installation still downloads through the authenticated SitePulse Connector endpoint; WordPress never receives or contacts a Google Drive URL. Attachments are bound to the original uploader's SitePulse user and Google account. If the original Drive file, that user's account authorization or the SitePulse-to-Google request is unavailable, the Connector reports `package_storage`; a fresh preview identifies the current failure category. Reconnect the original account for credential failures, check the original file/app access for missing or forbidden files, and check API server connectivity for network failures. The installing administrator's Google account cannot substitute for the uploader's account. Disconnecting Drive is allowed even when it is the user's last linked Better Auth account because SitePulse email/password authentication remains available. A `package_download` result instead indicates that WordPress could not reach SitePulse or the Connector request was rejected before storage retrieval.

For a `package_storage` result, create a fresh preview to obtain the current specific failure message before retrying. API warning events `drive.preview.failed` and `drive.download.failed` include only the failure category, optional Google HTTP status and request ID. They do not log credentials, file/account references or raw Google response bodies. HTTP 403 alone does not identify the exact Google policy or quota; HTTP 404 can mean the app lacks file access even when the user can see the file in Drive.

Transport diagnostics classify recognized timeout, DNS, TLS and connection error names/codes, including bounded nested causes. Unknown or mixed causes retain the generic network message; raw exception messages and socket addresses are never returned or logged. Redirect responses are inspected manually and rejected without following them, with a distinct `redirect` category and HTTP status, instead of being mislabeled as network failure. An unauthenticated connectivity probe receiving HTTP 403 proves an HTTP response was received for that probe only; it does not diagnose authorization for the actual package or rule out intermittent failures.

Automated tests use encrypted credential fixtures, mocked Google responses and dedicated disposable PostgreSQL. Coverage includes Drive-only default uploads, explicit database rejection, disconnected/unconfigured upload failures without persisted bytes, legacy reads, both plugin/theme leases, exact bytes, hash/size failures, missing files, disconnect/wrong-account/reconnect, authority changes, unauthorized uploads, deduplication, original retention and unsafe upload-session hosts. Preview tests cover HTTP 401/403/404/429/503 and network failures without leaking provider details, changed file bytes and delivery failure after a successful preview. They do not validate real Google OAuth/token refresh or actual WordPress upgraders.

Before production enablement, verify real consent/callback/reconnect/refresh/revoke and both package types on disposable staging sites, including a near-8-MiB ZIP, file mutation/deletion and owner removal. Review desktop/mobile and keyboard interactions. This local implementation does not deploy or modify production data.
