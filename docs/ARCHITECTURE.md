# Architecture

Post-MVP software management adds an explicitly opt-in Connector pull queue; earlier read-only/foundation statements below describe their original milestone. `site_management` tracks local consent/current credential generation; `software_operations` stores previews, bounded commands, receipts, actor/reason, status and deadlines. Verified tenant administrators create and confirm operations, and current Connector credentials claim/report only their own site. Sites serialize management and credential changes with row locks. Unknown outcomes are never reassigned automatically. WordPress native lifecycle/upgrader APIs handle only allowed plugin/theme operations and official package sources. See [software management](SOFTWARE_MANAGEMENT.md) for the current protocol and limits.

Monitoring responsiveness uses a validated operator-wide HTTP interval (default 300 seconds, range 60–3600). Existing first-failure/recovery confirmation remains 60 seconds, independent of WordPress cron. Shortened intervals tighten bounded batches of healthy, unleased jobs without postponing work. Connector freshness generates independent warning `stale_data` incidents under the same site lock used by heartbeat, disconnect and credential rotation. Only a valid increasing-sequence heartbeat resolves these incidents; connection resets never claim recovery. API and worker share the transactional recipient/outbox policy in `packages/database/client/incidents.ts`. Migration 0008 extends incident types without introducing Connector probe jobs. See [latency and acceptance](MONITORING_RESPONSIVENESS.md).

Site allowances are centralized in backend entitlement helpers with defaults in `packages/config`. Organization row locks serialize creation/restoration with allocations. The trusted database operator CLI and separate platform administration API validate changes and audit them atomically; tenant plan-edit APIs remain unavailable. Platform APIs require a verified Better Auth user in the validated server-only `PLATFORM_ADMIN_USER_IDS` UUID allowlist and grant cross-tenant access only to workspace identity, usage and entitlement changes. Tenant site/monitoring APIs still require membership. Preview snapshots detect changed plan, override, usage or update timestamps under the same row lock. Downgrades preserve existing sites and monitoring. See [ENTITLEMENTS.md](ENTITLEMENTS.md).

The browser uses a single public origin. Next.js renders public/auth pages and a server-rendered workspace; `/api/v1/*` is proxied to Fastify. The web server forwards only cookies for authenticated server fetches. Fastify is the sole API framework. PostgreSQL stores identity, organizations, sites, connector state, monitoring jobs, checks, incidents and notification deliveries. A separate worker expires stale heartbeats, probes eligible paired sites and sends queued email alerts. Authentication and alert email use a development file outbox or production Resend transport. Redis and billing are not enabled.

Better Auth owns account creation, password verification, signed cookies, session lookup, expiry, and revocation. The API exposes only a validated allowlist of auth routes; native Better Auth endpoints are not publicly mounted. Password hashing delegates to the maintained Argon2 implementation at `@node-rs/argon2`. Passwords use Argon2id with 19 MiB memory, 2 iterations, and one lane. API responses do not expose session tokens or hashes. Sessions last seven days and are read from PostgreSQL without a cookie cache, so revocation takes effect on the next API lookup.

The supplied schema is adapted to the auth library: credential hashes live in `auth_accounts.password_hash`, instead of duplicating the hash on `users`. `auth_sessions` and `auth_verifications` are necessary supporting tables. Better Auth owns verification and reset tokens; its verification callback populates `users.email_verified_at`. The adapter enables transactions for atomic reset-token consumption. Organization plans default to server-selected `free`; manual allocations affect site counts only, with payments deferred.

Registration creates an account and session; creating an organization is a separate onboarding step. Organization, owner membership, and organization-created audit event commit in one transaction. Organization queries join membership with the authenticated user ID. Tenant UUIDs are identifiers, never credentials. Non-members receive the same 404 as a nonexistent organization. Owners/admins may rename; members may read. Mutations lock the membership row within the transaction before writing, so concurrent revocation cannot bypass authorization. There are no public invitation, membership-edit, owner-transfer, or plan-edit endpoints yet.

Auth requests are limited to 10 per minute per connection IP per endpoint and API instance. Proxy forwarding headers are untrusted. In the Compose topology, the web proxy can share an IP across visitors, making throttling conservative. Shared rate-limit storage and authenticated proxy/client-IP handling are required before horizontal scaling or public launch. Origin validation applies to every POST/PATCH/PUT/DELETE, including login and registration. No cross-origin API access is enabled.

The initial API image runs TypeScript through `tsx` with installed workspace dependencies; its build command typechecks rather than emits a separate bundle. The web image uses Next.js standalone output. Runtime containers run as the non-root `node` user. A later optimization may prune API development dependencies once deployment behavior is verified.

Site operations authenticate the browser session, lock its organization membership, and then lock the site. Owner/admin writes require verified email. Site identity and organization cannot be changed by PATCH. The API never accepts plugin-supplied organization/user/role fields. Soft deletion revokes credentials and challenges, hides the site, and preserves audit history.

Pairing challenges and credentials contain 256 random bits and are stored only as SHA-256 hashes. Challenges expire after ten minutes and are consumed under a site row lock, serializing concurrent pairing, rotation, deletion, disconnect, and heartbeat. Possession of a code authorizes that site; pairing does not independently prove domain ownership. New pairing invalidates the prior credential and resets its monotonic heartbeat sequence.

The single-site WordPress plugin uses capability/nonce protected admin actions, non-autoloaded local options, HTTPS safe POST requests with no redirects, and WP-Cron single events. The credential is never rendered. It sends site ID, increasing sequence, connector version, and a bounded minimized inventory. No customer content, settings, passwords or remote commands are collected. Retries back off from 60 seconds to a 15-minute cap; sequence numbers are reserved before transmission, including on timeout. WP-Cron depends on WordPress execution and should be driven by system cron for predictable timing.

Heartbeat receipt uses database time. Duplicate/reordered sequences cannot refresh freshness. The worker scans at most 200 rows per transaction using SKIP LOCKED, emits one audit record per stale transition, and shares site locks with heartbeat. Paired sites with no first heartbeat also become stale. Fresh receipt restores active connector status independently of external HTTP/SSL status.

External monitoring seeds at most 200 missing jobs per sweep for paired sites with a valid credential; HTTPS sites get separate uptime and SSL jobs. Claims use SKIP LOCKED, unique tokens and 90-second leases, with at most four concurrent jobs per sweep. Network I/O runs outside transactions. Completion locks the site, then checks the job token, lease and current eligibility. Disconnect, rotation, deletion and re-pair delete old jobs under the same site lock, fencing old results. The worker has an outbound monitoring network and the internal database network, without publishing a port; PostgreSQL has only the internal network.

Two consecutive bad checks open one incident per site/type, enforced by an active-fingerprint unique index. A single failure is suspected; a single success during an incident is recovering; two successes resolve it. SSL warnings and critical failures share that incident and update severity. Administrator acknowledgement is idempotent and does not suppress checks or resolve the incident. State, result and audit writes commit together. Connection resets close incidents with a distinct reason rather than reporting recovery. Retries begin at 60 seconds and back off to the lesser of the normal interval and 960 seconds; recovery confirmation waits 60 seconds. Checks expire after 30 days and resolved incidents after 90 days, deleting at most 500 of each per sweep. Audit retention remains separate.

Registration and each probe validate all DNS answers through a shared public-address policy. Each socket pins one approved IP and preserves the target Host/SNI and certificate checks. Redirects repeat validation even for the same hostname, with three hops maximum and no HTTPS downgrade. A ten-second total budget bounds DNS and network waits; sockets also have five-second inactivity timeouts. Only standard HTTP(S) ports are allowed, headers are capped at 16 KiB and bodies are discarded immediately. SSL checks apply to the original HTTPS hostname, independently of the HTTP redirect destination. No remote WordPress execution is added. See MONITORING_ACCEPTANCE.md for semantics, operational limits and pending live acceptance.
