# WordPress plugin and theme management

This post-MVP milestone explicitly authorizes a narrow remote mutation protocol. Earlier foundation/read-only milestone exclusions still apply to those milestones; this feature never provides arbitrary shell, SQL, source editing or arbitrary URL execution. Uploaded ZIP installation is limited to the separately opted-in, tenant-scoped package library described below.

## Permissions and execution

- Better Auth session, verified email, trusted Origin and current workspace owner/admin membership are required for previews, confirmation, cancellation and manual review. Members may read inventory/results. Platform administrator status does not grant tenant access.
- WordPress management starts disabled. A nonce-protected local administrator action records explicit consent and the administrator user ID. The Connector rechecks that user's current capabilities for every operation and restores the original WordPress user after execution. Removing that user's capabilities or opting out prevents future execution. Multisite is unsupported.
- A site must have a current Connector poll (five minutes), a valid current site credential, active connection, and complete inventory less than one hour old. Preview records bind current inventory and credential version; changes invalidate confirmation/dispatch. Each batch is limited to 20 unique sites and one component/action.
- Confirmation is atomic across the selected sites; execution is independent. The same preview cannot create duplicate queued commands. A partial batch is never claimed to be an atomic WordPress transaction.
- Each site has at most one queued/running/unknown command, enforced by site row locking and a partial unique database index. Role, verified email, site, credential version, opt-in and inventory are checked again at dispatch. A credential can only poll/report for its own site. Audit events include actual actor, component/action, reason, batch, dispatch and sanitized result; no site secret, command token, plugin output or request body is logged.
- The Connector makes outbound authenticated HTTPS POSTs, with the existing safe HTTP transport. No inbound WordPress execution route or SaaS-to-site administrative fetch is added. Existing public monitor SSRF checks are unchanged.

## Operations and safeguards

Plugins/themes support install, activate, deactivate, update and uninstall. Theme deactivation switches to an explicitly chosen installed theme. Protect active components from deletion, protect parent themes and active plugin dependents, and refuse ambiguous plugin identifiers. The Connector cannot modify itself remotely.

Official installation/update metadata comes from the native WordPress.org API. Official package URLs must be HTTPS on exactly `downloads.wordpress.org`, match the selected component's slug and official plugin/theme ZIP path, and contain no query or fragment. Downloads use safe WordPress HTTP, TLS validation, no redirects, bounded timeouts and sizes. WordPress native upgraders validate/extract/install packages; update flow always uses a freshly resolved official package rather than an uploaded or client-supplied update URL. Custom Update URI updates are refused. No arbitrary URL, premium registry, shell command or credentials for FTP/SSH are accepted. File changes require WordPress direct filesystem access and respect `DISALLOW_FILE_MODS`.

## Attachment library and uploaded-package installation

New uploads use only the uploader's personal Google Drive, with the same scan, quota, deduplication and installation interfaces. Unavailable Drive configuration/connection/provider blocks creation without a database fallback. Old attachments remain readable and installable; identical ZIPs reuse existing entries without migration. The original Drive owner must retain verified owner/admin membership, and downloaded bytes must match the original size/SHA-256. Library deletion/disconnection retains Drive originals. See [Drive storage](GOOGLE_DRIVE_STORAGE.md) for configuration, OAuth, retention and acceptance.

Verified workspace owners/admins may upload a plugin or theme ZIP through **Attachment library**. The raw request is `application/zip`, limited to 8 MiB before parsing. The archive must have one valid lowercase slug root, detected automatically from archive entries rather than the ZIP filename or a user-supplied field and one unambiguous matching WordPress name/version header. The scanner rejects traversal, absolute/backslash paths, case collisions, unsafe file modes, encryption, unsupported compression, overlapping/mismatched local headers, file/directory conflicts, more than 10,000 entries, more than 40 MiB expanded data, files over 2 MiB, nested archives/executables and protected Connector packages. Code scanning is time/size bounded and blocks selected encoded evaluation, decompression-to-execution, request-evaluation and command-execution indicators. These rules reduce obvious risk; a clean result is not proof of safety or compatibility.

The library stores only new-package metadata, scanner results, SHA-256 and Drive references in PostgreSQL. ZIP bytes pass through the API transiently and are persisted only in Drive; legacy database bytes are preserved. A workspace is limited to 100 packages and 64 MiB of raw ZIP data. Reads return metadata/findings/fingerprints only. Tenant members may view the library; only verified owners/admins may upload/delete. Deletion is refused while a live operation references the attachment. Duplicate bytes within a workspace reuse the existing record.

Installation requires Connector 0.4.0+ and the **Also allow installation of workspace ZIP attachments that passed the current static scan** checkbox in WordPress **Settings → SitePulse**, in addition to ordinary remote management. After saving both settings, wait for a recent Connector poll before retrying the SitePulse preview. The server rechecks this separate capability at preview, confirmation, dispatch and package delivery. A package has no public URL: only the credential for the exact site and a fresh running-operation token may request it. The server rechecks operation generation, actor membership, scan version/result, size and hash, then returns the ZIP with `no-store`. The Connector downloads only from its stored paired HTTPS origin, sends Origin/Bearer/lease data, follows no redirects, enforces the 8 MiB limit, rechecks local consent and SHA-256 after download, invokes the native WordPress upgrader and always removes the temporary file. Updates remain official-only. Uploaded code can still execute its normal install/activation hooks; operators must trust the source, review findings and back up each WordPress site first.

The site administrator must back up WordPress files AND database before changes. SitePulse's VPS database backups cover SitePulse records, not client WordPress files/data. Activation and uninstall hooks execute the selected installed plugin's normal WordPress lifecycle code; a faulty plugin can crash PHP or remove plugin data. Compatibility, hosting limits and rollback remain the operator's responsibility. Dependency guards supplement WordPress validation but cannot discover undeclared business dependencies.

## Delivery, replay and uncertainty

Management uses a separate single-event WP-Cron hook every minute, without changing the 15-minute heartbeat. System Cron should execute due WordPress jobs every minute; ordinary WP-Cron depends on traffic. Dashboard refreshes results every ten seconds and does not trigger execution.

Preview expires after ten minutes; queued work expires after one hour. A claim has a one-minute start deadline. The server never automatically reassigns running work. Connector durably writes a receipt before mutation, stores its sanitized outcome before sending acknowledgement, and retries acknowledgement only. A lost claim response or PHP crash can leave the outcome unknown; at fifteen minutes a running operation is displayed/reconciled as unknown. No exactly-once execution guarantee is claimed across PHP/database crashes, local database restoration or external WordPress changes.

Inspect WordPress before clicking **Reviewed in WordPress**; this releases the batch's unknown entries without undoing changes. A later stale result cannot override reviewed/cancelled records. Cancellation affects unstarted work only. Revocation, disconnect and permission changes cannot undo already dispatched/in-flight operations. Clock synchronization is required between VPS and WordPress for the short start deadline. Run PHP jobs with a hosting execution timeout shorter than fifteen minutes; do not release an unknown operation while a PHP process may still be working.

Inventory collection follows software operations and normal successful heartbeats. Connector 0.4.0 also queues a due-now inventory event on upgrade (first request loading the new version), reactivation and transition to enabled management. Explicit **Sync inventory** requests invalidate the six-hour local security-scan cache so the next accepted inventory includes a fresh bounded code scan. A collection lock serializes these sources. Exceptions produce a sanitized `collection` failure and do not prevent future heartbeat scheduling. Inventory status is separate from management polling and heartbeat health; failed attempts retain the previous snapshot.

**Sync inventory** requests read-only collection on the next outbound management poll, including when mutations are disabled. Verified workspace owners/admins only; server checks membership, active paired site and current credential. Pending requests are idempotent, expire for dispatch after fifteen minutes, and new requests are limited to once a minute per site. A sync and a mutation are never leased in the same response. Request IDs and credential generations prevent stale/cross-site results completing a newer request. Only an accepted inventory upload establishes success. Automatic uploads without a request ID may refresh inventory but do not complete an explicit outstanding request.

**Reload results** only reads saved results. Cards show not-yet-synced, waiting, received, failed or timed-out states and last successful receipt/attempt times. No inventory is not a website outage. Generic failure codes are `network`, `rejected`, `collection`; no paths, exception messages or raw payloads are sent. If the failure report itself cannot reach SitePulse, the cloud cannot know the attempt failed: an explicit request remains pending until it succeeds or times out; consult WordPress Settings → SitePulse for local inventory status. Reports are not durably retried; the next collection updates status. Old Connectors cannot consume sync requests and will time out; upgrade to 0.4.0. Due-now scheduling still depends on traffic-driven WP-Cron or a system Cron trigger; no timing guarantee is claimed.

Missing plugin icons fall back to shared SVG artwork. Official plugin icon requests go directly from the browser to fixed `ps.w.org` HTTPS paths with no referrer; WordPress.org receives the browser IP and slug, never a site credential. No arbitrary image proxy is exposed.

## Direct actions and bulk selection

Queued, running and unknown operations lock new actions for their site in the software manager. Cards show the outstanding action and waiting/running/manual-review state alongside the last reported inventory. Direct actions, bulk selection and install previews exclude these sites; other eligible selected sites remain available and exact targets are shown in confirmation. An acknowledged queue submission remains visible even if the following reload fails; older in-flight poll results cannot overwrite that acknowledgement. Successful reads, including after reopening the page, derive locks from server operation state. Completion/failure/cancellation/expiry releases the lock; unknown requires the existing explicit WordPress review. The directory returns the latest 100 history records plus all outstanding queued/running/unknown records, deduplicated and ordered by creation time. No schema or Connector change is needed.

Card activate/deactivate/update/uninstall buttons open a modal for that component and its eligible installations among the selected sites. They do not populate or modify the bulk form. The dialog requires a change reason, shows the exact component/site pairs, validates with the existing server preview endpoint, and queues only after explicit confirmation. Cancelling or pressing Escape does not confirm. Editing the reason or replacement theme invalidates the preview. Theme deactivation requires an installed replacement on every affected site.

Checkboxes and the separate **Add to bulk →** action prepare the adjacent **Bulk operation** panel without requesting execution. **Select visible** applies to the current search results; hidden selections remain counted and listed. Site/type changes clear component selection. Choose up to 20 components and a shared action, then **Review selected items**. Only eligible installed targets are included: active components are not uninstalled, already active/inactive targets are excluded from activation/deactivation, and update requires an available WordPress.org update. The Connector remains protected. Install-by-slug remains available when no installed components are selected.

The browser coordinates existing one-component server batches, not a new durable multi-component job. It obtains server previews, confirms the first, waits for every target to succeed and receive fresh successful inventory, then rechecks the next immutable approved component/site targets and obtains a fresh preview before confirming. Server fingerprints, membership checks and the one-outstanding-command-per-site index remain authoritative. Remaining work stops on failed/unknown/cancelled/expired/missing results, changed targets/authority, network errors or a 75-minute wait timeout. No mutation is automatically retried. Earlier successes are not rolled back. Unused previews may appear in Recent operations and expire without execution.

**Keep the page open for multiple components.** Leaving/closing it or clicking **Stop remaining items** stops only unsubmitted components. Confirmed batches remain durable and may execute. An uncertain confirmation response must be inspected in Recent operations and WordPress before creating another command. Queue submission is not completion; WordPress Cron still determines pickup time. Uploaded-package installation requires migration 0014 and Connector 0.4.0; official-source actions retain the existing protocol.

## API endpoints

| Endpoint under `/api/v1`                                        | Authorization / purpose                                                                                |
| --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `GET /organizations/:organizationId/software`                   | Membership; inventory/capability, latest 100 operations plus outstanding operations; no command tokens |
| `POST /organizations/:organizationId/software/preview`          | Verified owner/admin; `{siteIds, command:{kind,action,slug,replacement?}, reason}`                     |
| `POST /organizations/:organizationId/software/:batchId/confirm` | Verified preview author; `{}`                                                                          |
| `POST /organizations/:organizationId/software/:batchId/cancel`  | Verified owner/admin; cancel preview/queued entries                                                    |
| `POST /organizations/:organizationId/software/:batchId/resolve` | Verified owner/admin; confirm manual review of unknown entries                                         |
| `POST /connector/software-poll`                                 | Current site bearer; `{siteId,enabled}`; one command or null                                           |
| `POST /connector/software-result`                               | Same site bearer, credential version and command token; `{siteId,operationId,token,code}`              |
| `POST /organizations/:organizationId/software/inventory-sync`   | Verified owner/admin; `{siteId}`; returns deduplicated `requestId`                                     |
| `GET /organizations/:organizationId/attachments`                | Member; package metadata, scan findings, fingerprints and quota only                                   |
| `POST /organizations/:organizationId/attachments/:kind`         | Verified owner/admin; raw `application/zip`, bounded scan/store or deduplicated reuse                  |
| `DELETE /organizations/:organizationId/attachments/:id`         | Verified owner/admin; delete only when no live operation references the package                        |
| `POST /connector/inventory`                                     | Current site bearer; inventory plus optional `inventoryRequestId`; accepted upload records success     |
| `POST /connector/inventory-failure`                             | Current site bearer; `{siteId,inventoryRequestId?,code}`; bounded failure code only                    |
| `POST /connector/software-package`                              | Exact site bearer and running-operation lease; return approved ZIP bytes, never a public URL           |

Result codes: `ok`, `disabled`, `unsupported`, `not_installed`, `already_installed`, `active`, `dependency`, `filesystem`, `package`, `wordpress_error`, `uncertain`. No plugin error messages are returned. Consult the site's protected WordPress logs for diagnostics without sharing secrets.

## Validation and staging acceptance

Automated API tests use the dedicated disposable `_test` PostgreSQL database. PHP tests use isolated WordPress doubles and perform no real network/file mutations outside temporary fixtures. They do not replace testing actual WordPress upgraders.

1. Back up two disposable single-site WordPress installations. Deploy migration 0014, upgrade Connector to 0.4.0, pair, enable ordinary management and separately enable uploaded-package installation, and run system Cron every minute. Verify upgrade/opt-in queues immediate inventory without waiting for a heartbeat; unchanged consent/page loads must not continually queue collection. Verify both permissions are disabled before opt-in and enabling ordinary management does not enable package delivery.
2. In Plugins & themes select both sites, install an official disposable plugin by slug, then activate, update where an update exists, deactivate and uninstall in separate confirmed batches. Check individual results and fresh inventory in WordPress; a repeated confirm must not repeat execution.
3. On one test site install a second official theme, switch to it, deactivate by switching back, update where available and delete the inactive theme. Verify active and parent themes cannot be deleted; active plugin dependents block deactivation/uninstall. Keep the Connector protected.
4. Check member read-only, unverified owner denied, cross-workspace IDs hidden, forged Origin denied, each site's bearer rejected for the other site, and queued work suppressed after local opt-out/member demotion/credential rotation.
5. Interrupt acknowledgement after a harmless operation. Confirm later receipt retries do not repeat the mutation. Simulate an abandoned claim: after fifteen minutes show unknown, block new work, inspect WordPress and explicitly resolve. Never simulate failures on a production/customer site.
6. Review desktop/mobile, empty states, missing icons, keyboard selection/focus, required reason, preview expiry/conflicts and partial failure results. Validate database migration using the normal backup-first VPS workflow.
7. With remote mutations disabled, click Sync inventory; observe waiting then receipt. Verify Reload results does not queue collection. On a disposable fixture simulate collection/rejected-upload failures: keep old inventory and show failure while polling remains healthy. Pause Cron: show timeout after fifteen minutes, then resume and request again. Rotate credentials while pending: old IDs/results cannot complete a new request. If networking is fully offline inspect local WordPress inventory status; do not expect the failed report to reach SitePulse.
8. Add one plugin to bulk, then click another plugin's direct action. Verify the modal names only that component and eligible sites, bulk selection stays intact, Cancel/Escape queues nothing, and Confirm queues it once. Select two harmless inactive plugins with checkboxes, choose activate, review exact targets and confirm. Verify the second is submitted only after the first succeeds and new inventory arrives. Check hidden search selections, Select visible, protected Connector, read-only controls, mobile layout and keyboard focus. On disposable fixtures test failure/changed inventory/stop/navigation: remaining items must not be submitted; already queued tasks remain visible. This is not an atomic multi-plugin change.
9. Upload a trusted disposable plugin ZIP under 8 MiB with one matching root/header. Verify metadata, fingerprint, quota and no source bytes appear in reads. Install it on both sites through preview/confirmation, then verify a foreign workspace, wrong site credential, stale/forged operation token, revoked actor and disabled local package permission cannot fetch it. Upload a harmless fixture containing a blocking indicator and verify it remains visible but cannot be installed. Verify delete is refused while referenced and succeeds after operations are terminal. Repeat with a disposable theme. Check proxy limits with a package close to 8 MiB and confirm a larger request returns 413.

Live WordPress/hosting acceptance must be completed on staging before enabling this capability for production sites. No production deployment or client-site changes are performed by local automated checks.
